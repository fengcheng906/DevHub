# 技术决策记录（DECISIONS）

记录每个重要技术选择**以及为什么**，避免以后忘记原因走弯路。

## D1：为什么用 Python + tkinter？

**决策**：v0.1 用 Python 标准库 tkinter 做界面，不装任何第三方界面库。

**原因**：
1. 用户的 Python 3.13 已装好，tkinter 是自带的——**零安装成本**
2. 项目成员（周承俊）正在学 Python，用同一门语言写产品，学习和研发同步
3. 文件整理工具不需要华丽界面，tkinter 完全够用
4. 没有云端/付费依赖，符合"本地、免费、简单、稳定"原则

**将来可能推翻的条件**：如果需要复杂界面（拖拽、主题美化），再考虑 PySide6 等方案，并把 tkinter 版本存档。

## D2：核心逻辑与界面分离（core.py / app.py）

**决策**：所有文件操作写在 core.py，界面只调用，不直接碰文件。

**原因**：
1. 核心逻辑可以自动化测试——界面很难自动测试，逻辑不该被它拖累
2. 以后做"自动化任务中心"（阶段 3）时，可以复用 core.py 而不需要界面
3. 出问题时能快速定位：是逻辑错了还是显示错了

## D3：撤销机制用"日志回放"而不是"回收站"

**决策**：每次执行后写 JSON 日志（记录 from/to），撤销时反向移动。

**原因**：
1. 不依赖 Windows 回收站 API，跨场景可靠
2. 日志同时是"操作审计记录"，对以后做业务管理模块有用
3. 实现简单，v0.1 就能有完整撤销能力

**已知限制**：如果用户整理后又手动移走文件，撤销时该文件会跳过并提示（不强行覆盖）。

## D4：整理只作用于文件夹第一层，不递归

**决策**：v0.1 只扫描所选文件夹的第一层文件。

**原因**：初学者第一次用，行为越可预测越安全。递归选项排进 v0.2，并会同样带预览。

## D5：不直接复用"月度计划里的重命名助手"？

**背景**：研发启动时核查过，月度计划 W2 的"批量文件重命名助手"尚未开发（当时只完成了 W1）。
因此本产品为全新开发，无历史代码可复用。批量重命名功能排入 v0.2，届时作为工作台的一个功能加入，而不是单独的小脚本——一步到位做成产品。
